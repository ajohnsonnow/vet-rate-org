# Design tokens

> Single source of truth for color and sizing tokens: [tokens/source/](../tokens/source/). Style Dictionary v4 emits CSS variables, a Tailwind-shaped JS module, and a markdown reference. Closes finding #26 in [AUDIT_FINDINGS.md](./AUDIT_FINDINGS.md).

**Last updated:** 2026-05-15

---

## The shape

```
tokens/source/
├── colors.json     # service-blue, tactical-grey, medal-green, warning-gold, paper, tbi, aaa, protected
├── sizing.json     # touch-target.min (44px), ring.thick (3px)
├── aliases.json    # va-blue, va-gold (legacy aliases — see below)
└── typography.json # font.base-lg

style-dictionary.config.mjs    # Style Dictionary v4 config (custom Tailwind-shape format)
scripts/build-tokens.mjs       # `npm run build:tokens` runner

src/generated/                 # COMMITTED outputs (regenerated by build:tokens)
├── design-tokens.css          # CSS custom properties (--color-service-blue-900: …)
└── design-tokens.js           # CJS module consumed by tailwind.config.js

docs/DESIGN_TOKENS_REFERENCE.md  # generated reference table (this doc explains how; that one lists the values)
```

## How to add or edit a token

1. Edit the relevant `tokens/source/*.json`. Format follows [Style Dictionary's spec](https://styledictionary.com/info/tokens/):
   ```json
   {
     "color": {
       "new-palette": {
         "500": { "value": "#aabbcc", "comment": "primary shade" }
       }
     }
   }
   ```
2. Run `npm run build:tokens`. This invokes `npx --yes style-dictionary@^4.0.0` — Style Dictionary is **not** a `devDependency`; it's fetched on demand (see "Why npx-on-demand" below).
3. Commit both the source file *and* the regenerated outputs in [src/generated/](../src/generated/).
4. Tailwind picks the new palette up automatically — `bg-new-palette-500`, `text-new-palette-500`, etc. all work.

---

## Why npx-on-demand instead of a devDependency

The trade-off (mirrors [PREFLIGHT_EXTRAS.md](./PREFLIGHT_EXTRAS.md)):

| | Always-on devDep | npx-on-demand (this approach) |
|---|---|---|
| `npm ci` time | +~3 s for Style Dictionary + transitive deps | unchanged |
| `package.json` clutter | +1 devDep line | 0 devDep lines |
| First-run latency | 0 s | ~20 s (npx fetch on first invocation) |
| Subsequent runs | 0 s warmup | 0 s (npx cached) |
| CI cache friendliness | excellent | good (npx caches between runs) |
| Generated outputs committed | yes | yes |

Because **the generated outputs are committed**, a clean clone builds the app *without* running `build:tokens`. The script is only needed when you edit tokens or want to verify drift in CI.

This keeps Style Dictionary off the critical path while still giving us a real, audit-closing token pipeline.

## How Tailwind consumes the tokens

[tailwind.config.js](../tailwind.config.js) imports the generated CJS module and spreads it into `theme.extend.colors`:

```js
const generatedTokens = require('./src/generated/design-tokens.js');

module.exports = {
  theme: {
    extend: {
      colors: {
        ...generatedTokens.colors,
        // Legacy aliases override the generated literals so runtime
        // theming via :root CSS vars still works.
        'va-blue': 'var(--va-blue, #2d5016)',
        'va-gold': 'var(--va-gold, #88b04b)',
      },
    },
  },
};
```

The generated `design-tokens.css` is **not** imported by default. It's available to any component that wants runtime CSS-variable theming (e.g., a future user-customizable theme picker) by importing it explicitly. Most usage flows through Tailwind utility classes today.

## CI drift gate

`npm run build:tokens:verify` re-runs the build and exits **2** if the generated files would change. Wire into CI to catch the case where someone edits tokens/source/*.json but forgets to regenerate:

```yaml
# .github/workflows/ci.yml (optional step)
- name: Token drift check
  run: npm run build:tokens:verify
```

This is **not** wired by default — Style Dictionary's first-run fetch (~20 s) is a meaningful CI cost. Promote to a blocking gate if drift becomes a recurring issue.

## What we explicitly chose NOT to do

- **No Figma Variables sync.** This is a solo-developer open-source project with no Figma source of record. If a design partner joins, revisit the [Figma → Style Dictionary plugin path](https://www.figma.com/community/plugin/888356646278934516/design-tokens) — it would emit the same `tokens/source/colors.json` shape we already use.
- **No Code Connect.** Same reason — there's no Figma component library to bind to.
- **No iOS/Android targets.** The app is a browser SPA; emitting `Colors.kt` or `UIColor.swift` would be dead code. If a wrapper app ships, add the platforms to [style-dictionary.config.mjs](../style-dictionary.config.mjs) — Style Dictionary's selling point is exactly this kind of late binding.
- **No token versioning.** Tokens evolve with the rest of `src/`; semver carried by the app version is enough. If we ever publish the tokens as their own npm package, version them then.

## Re-audit triggers

Reopen this document if any of these happen:

- A second consumer (mobile wrapper, browser extension, partner-branded site) needs the same tokens — Style Dictionary platforms make this nearly free; document the new target here.
- Tailwind's `theme.extend.colors` grows a second source of truth (e.g., a third-party plugin contributes colors that aren't in `tokens/`).
- A user-customizable theme picker ships — switch components to read from `var(--color-…)` rather than Tailwind utilities, and update this doc.
