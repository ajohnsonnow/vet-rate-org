# Supply chain — what we ship + how to verify it

Closes [AUDIT_FINDINGS](AUDIT_FINDINGS.md) **#20** (supply-chain-security) and **#21** (devsecops-pipeline).
The earlier S8 partial-close pinned the structural pieces (npm
`overrides`, dependabot grouping, CycloneDX + SPDX SBOMs). B19 closes
the two residuals the S8 entry called out:

1. Artifact signing — **Sigstore keyless cosign** via GitHub OIDC.
2. SLSA provenance — **SLSA Level 3** attestation via the
   `slsa-framework/slsa-github-generator` reusable workflow.

Both are wired into [.github/workflows/release.yml](../.github/workflows/release.yml).
No key management is required — Sigstore takes a short-lived OIDC
token from GitHub's identity provider and signs against the public
transparency log.

## What every release ships

For each `v[0-9]+.[0-9]+.[0-9]+` tag, the release page attaches:

| Asset | What it is |
|---|---|
| `sbom.cdx.json` | CycloneDX 1.5 SBOM, prod deps only (`npm sbom --omit=dev`) |
| `sbom.cdx.json.sig` | Cosign signature over the CycloneDX SBOM |
| `sbom.cdx.json.pem` | Sigstore-issued certificate (binds signature → workflow identity) |
| `sbom.spdx.json` | SPDX 2.3 SBOM, prod deps only — same content, different schema |
| `sbom.spdx.json.sig` + `.pem` | Cosign signature + cert for the SPDX SBOM |
| `dist.tar.gz` | The production build output (`dist/` directory, tarred + gzipped) |
| `dist.tar.gz.sig` + `.pem` | Cosign signature + cert for the dist tarball |
| `vet-rate-org-vX.Y.Z.intoto.jsonl` | SLSA Level 3 provenance attestation |

## Verification recipes

### Verify a Sigstore signature (any of the signed assets)

```bash
# Replace <owner>/<repo> with the actual GitHub coordinates.
cosign verify-blob \
  --certificate-identity-regexp '^https://github.com/<owner>/<repo>/.github/workflows/release.yml@' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate sbom.cdx.json.pem \
  --signature sbom.cdx.json.sig \
  sbom.cdx.json
```

What this proves: the file was signed by the
`release.yml` workflow running in the named repository under GitHub
Actions' OIDC issuer. A forged signature would either fail certificate
verification or surface an unexpected identity in the cert subject.

### Verify the SLSA-3 provenance

```bash
# slsa-verifier ≥ v2.5.0 — see https://github.com/slsa-framework/slsa-verifier
slsa-verifier verify-artifact dist.tar.gz \
  --provenance-path vet-rate-org-vX.Y.Z.intoto.jsonl \
  --source-uri github.com/<owner>/<repo>
```

What this proves: the artifact was built by the verified workflow from
the verified source repository, using a hosted GitHub runner — the SLSA
L3 isolation properties (the build process is non-falsifiable, the
provenance is generated by a separate trusted process, the build is
hermetic at the repo+workflow level).

### Verify the SBOM content matches the deployed bundle

```bash
# Recompute the digest of the on-disk SBOM and compare to the
# transparency-log entry referenced by the cert chain.
sha256sum sbom.cdx.json
# Then look up the digest in the Rekor public log:
rekor-cli search --sha sha256:<digest>
```

## Threat model — what these controls do and don't cover

| Threat | Mitigated by |
|---|---|
| Tampered SBOM | cosign signature over SBOM + Rekor transparency-log entry |
| Tampered dist bundle | cosign signature + SLSA provenance bound to source ref |
| Compromised maintainer publishing a malicious release | Provenance shows the build was NOT from this workflow; verifier refuses |
| Compromised GitHub Actions runner (rare, but in scope for SLSA L3) | SLSA L3 build isolation; provenance generator runs in its own job with its own OIDC identity |
| Compromised upstream npm package | Out of scope here — see Dependabot + `npm audit --omit=dev --audit-level=high` gate in [ci.yml](../.github/workflows/ci.yml) |
| Compromised dev workstation | Out of scope — Sigstore identifies the *workflow*, not the developer |
| Force-pushed tag pointing at a poisoned commit | Provenance ties to the commit SHA, not the tag; verifier sees the mismatch |

## Why not in-toto attestations / Cosign keyed signing / per-package signing?

- **Keyed signing** (long-lived cosign key, GPG, etc.): we don't have a
  key-management story for a one-developer project. Sigstore keyless
  is the right ergonomic choice for this scale.
- **Per-package signing**: this app is delivered as a static-built SPA,
  not a published npm package. The dist tarball is the unit users care
  about.
- **Custom in-toto attestations** (SPDX, vuln scan, etc.): the SLSA
  provenance already carries the build-trigger context. Custom
  attestations would need a downstream consumer to read them; none
  exist for this project yet.

## IaC scanning — residual

The audit row #21 also listed IaC scanning (Terraform, Helm, …) as a
gap. We have no IaC: the app is a static SPA, no servers, no k8s, no
cloud-deploy config beyond a host's static bucket. Marking IaC
scanning as intentionally **n/a** in spirit, but the audit row stays
`compliant` rather than n/a because the rest of the DevSecOps pipeline
fully applies.

## Re-audit triggers

- Adding a server-side surface (Workers, Functions, custom Node host) —
  reopens IaC scanning + adds runtime-secrets management.
- Adopting npm publish for a package — adds per-package signing as a
  new asset class.
- Sigstore root rotation (rare; check `cosign verify` failures first).
- Pinned SLSA generator version (`@v2.0.0`) — bumping is a verifier
  break, downstream consumers will see the source ref change. Document
  the bump in this file and the release notes.
