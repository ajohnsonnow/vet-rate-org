# VSO multi-veteran silos: spec (final)

**Status:** Decisions recorded 2026-09-24 (§9). Ready to build in the sprint order in §10. This spec is **not done** until Cole's implementation passes Vera's independent verification (V1, V2) and Anth signs off (R).
**Companion:** [VSO_ENCRYPTION_BRIEF.md](./VSO_ENCRYPTION_BRIEF.md) (brief B, per-veteran encryption). It is required before VSO mode can be turned on in production (F1).
**Citations:** Re-checked on 2026-09-24 for `cloudEncryption.js`, `storage.js`, `autoBackup.js`, `veteranKnowledgeBase.js`, `myPacketManager.js`, `pdfExtractor.js`, `userDocSemanticIndex.js`, `bugReportStorage.js`, `featureRequestStorage.js`, `unifiedAIService.js`, `ThemeContext.jsx`, `migrationManager.js`, `main.jsx`, `useBootSequence.js`, `persistentStorage.js`, `DeviceKeystorePanel.jsx`, `featureFlags.js`, `debugDump.js`. Other line numbers are carried over from the draft, so Cole re-checks them when he touches a file.

**The recon finding that shapes this spec.** The app has no multi-user code today. `VSO` only shows up as a glossary term ([HelperModeContext.jsx:63](../src/contexts/HelperModeContext.jsx#L63)) and in VSOFinder. "Affiliation" means theme palettes ([affiliations.js](../src/config/affiliations.js)), not user accounts.

`localStorage` is used directly in **101 non-test files** under `src/`, and the keys are string literals spread across those files with no shared key registry. So "add a veteran prefix to every key" would mean changing about 100 files, and any key added later would leak by default. The design below avoids that. It **swaps out everything that isn't device data**, and gives each veteran its own IndexedDB database names. There are only 11 places where a database is opened (8 `indexedDB.open` calls and 3 `idb-keyval` importers), so the second part is cheap.

## 1. Commander's intent

- **PURPOSE:** Let a VSO help several veterans on one device. No veteran's data may ever appear, be readable, or be written inside another veteran's workspace, and parked data must be encrypted at rest.
- **KEY TASKS:**
  - a veteran registry
  - swap non-device `localStorage` in and out on switch
  - separate IndexedDB names per veteran
  - a full page reload on switch
  - a guard against a second open tab writing to the wrong veteran
  - a "You are working on" banner
  - create, rename, delete and export
  - move existing data into the first veteran with no copying
  - per-veteran encryption (brief B)
  - the policy gates recorded in §9
- **END STATE:** Vera's leakage suite (§7) and the encryption suite (brief B §7) pass in Chromium and Firefox. Users who never turn on VSO mode see no change. Production stays behind `VITE_VSO_MODE_ENABLED=false` until both suites pass and Anth signs off.

## 3. Architecture

**3.1 Registry and state.** These are stored in shared `localStorage` (device keys):

- `vetrate_vso_registry`: `{ version:1, silos:[{id, initials, caseRef, createdAt, lastOpenedAt, authAckAt, reviewBy|null, legacy:bool, deleting:bool, enc:"none"|"migrating"|"complete"}] }`.
  - `id` is a `crypto.randomUUID()` shortened to 12 hex characters.
  - The display label is `${initials} · ${caseRef}` (Q6) and is derived from those fields, never stored.
- `vetrate_active_silo`: the active veteran's id.
- `vetrate_silo_switch_journal`: exists only while a switch, lock or unpark is in progress.
- `vetrate_vso_idle_minutes`: the idle auto-lock setting (brief B §3.5).

If there is no registry, VSO mode is off and every code path below does nothing. **If a registry exists, the VSO code paths run whatever the build flag says**, so data is never stranded (§3.7).

**3.2 Deciding what is shared.** One module (`src/utils/siloScope.js`, name up to Cole) exports `isDeviceKey(key)` and uses an **explicit** device list: exact names plus the keystore prefixes. The list covers:

- display and accessibility: theme, colour-blind mode, reduced motion, font size, `vetrate_language` (Q7, device preference), helper mode and tooltips, focus mode, the tour-completed flag
- AI and runtime settings: local AI model, experimental WebGPU, selected GPU, GPU preference, token limit config, AI mode, AI preset, swarm config, wllama config and cache, local server config
- `vet_rate_last_seen_version`, `pwa_install_dismissed`, `vetrate_system_status`, `vetrate-mobile-notice-dismissed`
- the four `vetrate_vso_*` / `vetrate_silo_*` / `vetrate_active_silo` keys in §3.1
- `vet_rate_kek_*`, `vet_rate_wrapped_key_*`, `vet_rate_rotating_key_*`, `vet_rate_backup_key_*`

Every other key belongs to a veteran. There is no list of veteran keys to maintain.

**3.3 Separate database names.**

- `siloDbName(base)` returns `base` for the legacy (first) veteran and `${base}__s_${id}` for every other veteran.
- It reads `vetrate_active_silo` **once, when the module loads**. That is safe because every switch reloads the page.
- All 8 hand-written `indexedDB.open` calls plus the 3 idb-keyval importers change to use it. Nothing else is touched.
- The per-veteran base names are one exported constant list, used by delete (§4) and by Vera's suite. Shared names (`VetRate_DKB`, `vet-rate-dbq-cache`, model caches) must never appear on it.

**Fix (SPEC-DEFECT-1, found 2026-09-24).**

- The problem: the boot migration ([useBootSequence.js:37-72](../src/features/boot/useBootSequence.js#L37), called at [:139](../src/features/boot/useBootSequence.js#L139)) checks for the migrated marker in the keyval store. A new veteran's keyval store has no marker, and device keys such as `vet_rate_last_seen_version` are always present ([storage.js:148-149](../src/utils/storage.js#L148)). So [storage.js:178-203](../src/utils/storage.js#L178) would copy **all of localStorage, including keystore material and the registry**, into every new veteran's store.
- The fix: when a veteran is created, write `vet_rate_migrated_to_indexeddb = "true"` into that veteran's keyval store.

**3.4 Switch, lock and boot sequence** (amended 2026-09-24 for brief B: loading the incoming veteran now happens at boot, behind the unlock screen).

A _switch_ goes from A to B. A _lock_ is the same sequence with `to = from`. Both run in the tab that starts them, under the web lock `vetrate_silo_switch`:

1. Send `switch-begin` on `BroadcastChannel("vetrate-silo")`. Write the journal as `{from, to, phase:"begin"}`. Cancel any pending auto-backup: add a `cancelPendingBackup()` export next to [autoBackup.js:421](../src/utils/autoBackup.js#L421).
2. Park A:
   - Copy every veteran key currently in localStorage into A's `VetRate_SiloSnapshot` store (one record, overwritten each time). With brief B it is sealed with A's key.
   - Read it back and check it matches (with B, open and compare), then set the journal to `phase:"parked"`.
3. Remove every veteran key from localStorage, using the browser's own `removeItem`.
4. Set `vetrate_active_silo` to `to`, delete the journal, run `sessionStorage.clear()`, then `location.reload()`.

**Boot.** A pre-boot module is imported first by [main.jsx](../src/main.jsx). The app graph, currently statically imported at [main.jsx:18-20](../src/main.jsx#L18), is loaded with a dynamic `import()` only after step 8. This stops any app module from reading storage before unpark.

- **Step 5, journal recovery:**
  - `begin`: throw away the journal and stay on `from` (their localStorage was never touched).
  - `parked`: redo steps 3 and 4 (safe to repeat).
  - `unparking`: remove every veteran key, then redo step 8.
- **Step 6, stale sessionStorage:** if sessionStorage `vetrate_session_silo` doesn't match the active veteran, clear sessionStorage and set the marker.
- **Step 7, with brief B:** show the unlock screen, unwrap the active veteran's key, and drop the device key from memory (brief B §3.5).
- **Step 8, unpark:**
  - **No veteran keys in localStorage:** write the journal `{phase:"unparking", silo}`, load the active veteran's snapshot (if any) into localStorage using the browser's own `setItem`, then delete the journal.
  - **Veteran keys present** (the last session closed without locking): keep them, because they are newer than the snapshot. Show the notice "Last session wasn't locked."
- **Step 9:** load the app with a dynamic import and render it.

**3.5 Guard for other open tabs.**

- A guard wraps `localStorage.setItem`, `removeItem` and `clear` from the pre-boot module. It is installed before anything else loads, including before `initAutoBackup` at [useBootSequence.js:141](../src/features/boot/useBootSequence.js#L141).
- For veteran keys it **drops the write** if either:
  - the live `vetrate_active_silo` doesn't match the veteran this tab loaded with, or
  - a switch journal exists.
- Any tab that gets `switch-begin` shows a blocking notice, "Another tab is switching veterans. This tab will reload."
- A `storage` event on `vetrate_active_silo` reloads the tab.
- The outcome: a write made in another tab during a switch is **lost, not leaked**, and the user is told.

**3.6 Rejected alternatives** (for ADR-003):

- Adding a prefix to keys at all ~101 call sites: any new key leaks by default.
- A proxy on `Storage.prototype` that rewrites keys: breaks the `key(i)`/`length` loops at [cloudEncryption.js:463-464](../src/utils/cloudEncryption.js#L463) and [storage.js:180](../src/utils/storage.js#L180).
- A separate subdomain per veteran: the strongest isolation, but it re-downloads multi-GB AI models for every veteran and needs DNS changes.

**3.7 Feature flag.**

- Build-time `VITE_VSO_MODE_ENABLED`, default `false`, following the [vaAuth.js:25](../src/config/vaAuth.js#L25) pattern.
- It gates only the **entry point**: the "Help more than one veteran" setting is not rendered when the flag is off.
- It must **not** use [featureFlags.js](../src/utils/featureFlags.js), which fails open (unknown features return `true` at [featureFlags.js:176](../src/utils/featureFlags.js#L176)).
- Production turns the flag on only after V2 passes and Anth signs off (F1).

**3.8 Policy gates in VSO mode** (these apply whenever a registry exists):

- **Cloud backup off (F2):** cloud sync and MultiCloudManager's provider actions are disabled. [DeviceKeystorePanel](../src/components/DeviceKeystorePanel.jsx), which is only rendered inside [MultiCloudManager.jsx:1633](../src/components/MultiCloudManager.jsx#L1633), **stays reachable**, because the VSO needs passphrase change, recovery-bundle export and deauthorize.
- **Cloud AI (Q4):** off by default.
  - [isCloudAIAvailable](../src/utils/unifiedAIService.js#L532) and [generateWithCloudAI](../src/utils/unifiedAIService.js#L1023) refuse unless the active veteran's `vetrate_ai_consent === "true"`. Enforcing it in the service covers AUTO mode ([unifiedAIService.js:745-746](../src/utils/unifiedAIService.js#L745)), not just the three components that check consent today.
  - Turning on VSO mode removes the legacy veteran's existing consent, so the VSO re-affirms it on that veteran's behalf.
  - In VSO mode the consent prompt reads "Has this veteran agreed to have their information sent to Google Gemini?"
  - The Gemini key is swapped per veteran.
- **No automatic plaintext file writes:**
  - The auto-download at [autoBackup.js:233-237](../src/utils/autoBackup.js#L233) is off and its toggle is disabled.
  - The milestone and manual download paths in [persistentStorage.js](../src/utils/persistentStorage.js#L516) only run when the VSO explicitly asks.
  - Every explicit export shows "This file is not encrypted. Store it somewhere safe and delete it when you're done."

## 4. What the VSO sees

- **Turning it on:** the setting "Help more than one veteran (VSO mode)" lives in the existing device-settings surface (Cole picks it; [AccessibilityMenu.jsx](../src/components/AccessibilityMenu.jsx) already holds device settings such as the Gemini key at :12). Do not create a new settings page. The wizard:
  1. Explains what changes, links the help page (Q8), and recommends full-disk encryption.
  2. Requires a device passphrase. If none is set, it sets one (VSO mode requires at least 12 characters). It then offers a recovery-bundle download.
  3. Asks "The information already in this app belongs to:" with initials and case-reference fields (Q6), plus the authorization checkbox (Q3).
  4. Migrates and encrypts the existing data (brief B §3.9), with progress shown.
- **Banner:**
  - Shown only in VSO mode, always visible in [AppHeader.jsx](../src/features/header/AppHeader.jsx): **"You are working on: {label}"**, with **Switch veteran** and **Lock** buttons.
  - Must fit at 390px and 3840px without horizontal scrolling, with touch targets of at least 44px and WCAG 2.2 AA contrast in every palette.
  - After a switch or unlock, move focus to the main heading and announce "Now working on {label}" once in a polite live region.
- **Switching:**
  - A dialog lists veterans by label, last-opened date and a "Review due" badge.
  - Choosing one shows "Switch to {label}? Anything not yet saved for {current} stays with {current}."
  - Then a full-screen "Switching…" message, a reload, and the unlock screen.
- **Adding:** "Add a veteran" asks for:
  - initials (1–4 letters)
  - a case reference
  - an optional "Review by" date (Q5)
  - the required checkbox **"I am authorized to act for this veteran (for example, VA Form 21-22 or 21-22a is on file)."** (Q3). `authAckAt` is recorded.

  It also asks for the device passphrase (brief B §3.6), then switches into an empty workspace.

- **Label rules (Q6):** Initials are letters only, 1–4 characters, with periods allowed. The case reference is up to 24 characters of `A–Z a–z 0–9 space - _ / # .`.
  - _Blocked:_ any SSN-shaped value (`\d{3}[-\s]?\d{2}[-\s]?\d{4}`) or 8–9 digits in a row with an optional `C` prefix (a VA file number), in either field. The error text says why.
  - _Warned, not blocked:_ a case reference that looks like a name (two or more capitalised alphabetic words): "Don't use full names. Use your organisation's case number."
- **Renaming:** changes the registry fields only. The same rules apply.
- **Retention reminder (Q5):**
  - When `reviewBy` has passed, the switcher shows "Review due" and the banner shows one dismissible notice per session: "This veteran's review date has passed. Decide whether to keep or delete their workspace."
  - **It never deletes anything, schedules deletion, or blocks work.**
- **Deleting:**
  - Not allowed for the active veteran ("Switch to another veteran first").
  - The VSO types the label and enters the device passphrase.
  - Deletion destroys the veteran's key first, then their databases and registry entry (brief B §3.7).
  - The message says plainly: "This cannot be undone and does not touch other veterans."
- **Exporting:**
  - Only for the active veteran, using the existing BackupManager export.
  - Downloaded file names use the veteran's 4-character short id, **never the label**. This includes [autoBackup.js:279](../src/utils/autoBackup.js#L279).
  - Every export shows the "not encrypted" warning (§3.8).

## 5. Moving existing single-user data into the first veteran

The existing data becomes the legacy veteran (`legacy:true`). Its localStorage stays where it is and its databases keep their current unsuffixed names, so **nothing is copied**. The wizard then encrypts it in place (brief B §3.9). The first lock or switch parks the legacy veteran's localStorage.

Turning VSO mode **off** is only allowed when one veteran remains. It decrypts that veteran's records back to plaintext (brief B §3.9, reverse), removes the registry, removes the veteran's key, and leaves the data live.

## 9. Decisions and open questions

- **F2, cloud backup:** Off in VSO mode (§3.8). The device-passphrase panel stays reachable.

- **Q7, language:** A device (VSO) preference (§3.2).
- **Q4, cloud AI:** Off by default in VSO mode. It needs consent per veteran, enforced at the service level. The Gemini key follows the swap rule (per veteran) (§3.8).
- **Q8, help page:** The zero-code help page ("one browser profile per veteran") ships now as S0, independent of the flag.
- **Q3 and Q5, legal:** These stay open for counsel. The product safeguards that ship whatever counsel decides are the authorization-acknowledgement checkbox and the optional retention reminder. **Neither may auto-delete anything.**

**Legal questions still open (to answer before any public announcement; not code gates):**

- **Q3:** Does a VSO's Terms of Service acceptance cover the veterans they enter data for? Is written veteran consent (e.g. VA Form 21-22/21-22a) required, and does the app need to show a notice? The ToS keys are currently device-level.

**Deviations and flags found while finalising (need Anth's call where marked):**

- **Open question:** Should brief B later cover single-user mode too? [storage.js:218-220](../src/utils/storage.js#L218) still records plaintext as security debt.
