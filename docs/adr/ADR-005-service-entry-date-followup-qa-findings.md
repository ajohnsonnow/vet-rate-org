# ADR-005: Service entry date follow-up — closing the gaps QA found in ADR-004

**Status:** Accepted; superseded in part by ADR-007 (2026-09-27) — every Open Issue below is now closed or superseded; see the amendment note at the end of this document.
**Date:** 2026-09-27
**Context:** QA re-review of ADR-004 (`docs/adr/ADR-004-service-entry-date-single-source-of-truth.md`) found that several of its claims did not hold once the real write paths (Muster Call's Verify & Save re-persist, My Packet's manual editors, FormsHelper) were driven end to end, rather than exercised through a single mocked edit per consumer.

---

## Context

ADR-004 shipped `pickServiceEntry` and `getServiceEntry()` as the one selector shape-1 consumers read, and claimed every editor "writes the veteran's correction through to the canonical period." QA's re-review (harness driving the real `persistFormationDocument`/`autoPopulateProfile`, an in-memory VKB store standing in for IndexedDB) found that claim was false in two concrete, reproducible ways, plus several narrower gaps:

1. **D11-1 was not actually fixed end to end.** Muster Call's Verify & Save re-runs `persistFormationDocument` for the same file with the corrected fields spliced in (`useSequentialFormationFlow.js`'s `runVerifyAndSave`). That re-run goes through `upsertServicePeriod` → `_mergeExistingServicePeriod`, which treats `serviceStartDate` as the period's identity key (never merged) and explicitly skips `serviceStartDateDerived` in its generic per-field loop. So a correction landed in `profile.serviceStartDate`/`dd214Data.entryDate` but **never** in `servicePeriods[]` — and `getServiceEntry()` reads periods first, so `aiSystemPrompts.js`, `dossierExport.js`, and the Service span kept showing the original calculated guess with its marker, while `profile.serviceStartDate` and FormsHelper's prefill disagreed with them. ADR-004's own paragraph on this ("Verify & Save clears `serviceStartDateDerived` in `verifiedData`") was true of the _payload_, not of what that payload does once it reaches the canonical store on re-persist.
2. **The manual-editor "flat mirror" sync could silently downgrade a real date to a guess.** `_syncFlatServiceStartDateMirror` (added by ADR-004 for `addServicePeriod`/`updateServicePeriod`/`removeServicePeriod`) recomputes `profile.serviceStartDate` from `pickServiceEntry` on **every** period write, including one that only touched an unrelated field on a different, still-calculated period. If a veteran had separately corrected `profile.serviceStartDate` through FormsHelper (non-derived), an unrelated My Packet edit clobbered it with the calculated guess — violating standing decision 3 ("never silently lose a value").
3. **ADR-004's claim that "My Packet's Service tab editor and FormsHelper already wrote through correctly … no change needed" was false for FormsHelper.** `FormsHelper.jsx`'s `handleSaveProfile` writes only `profile.serviceStartDate`/`serviceStartDateDerived` via `saveVeteranProfile` — it never touches `servicePeriods[]`. Since `FormsHelper.jsx` is outside this fix's file ownership (per the task boundaries), the correction cannot be made to write through at the source.
4. **`pickServiceEntry` implemented "earliest wins," not the precedence ADR-004 described.** A calculated (derived) period chronologically earlier than a corrected/printed one still won, which surfaces concretely whenever a >7-day-away correction can't merge into the existing period (`isSameServicePeriod`'s tolerance) and `upsertServicePeriod` creates a second period instead — the stale calculated one, being earlier, kept being reported as "the" entry date.
5. Several narrower, confirmed gaps: the review modal's live "(calculated from net service)" marker stayed on an already-edited value until Save; `dossierExport.js`'s Service Dates line paired the canonical start with an unrelated period's end date; a VKB viewer Entry Date edit only propagated to `servicePeriods[]` when the two dates were byte-identical (no tolerance for the two independent write paths having already drifted); a corrected entry date left a duplicate "(calculated)" enlistment event on the evidence timeline (`(date, eventType)` dedup treats a corrected date as a new event); and data saved before this fix's migrations existed (a code-sheet-corrected period whose `serviceStartDateDerived` predates the `authoritativeDates` bypass) had no migration path.

## Decision

Fixed within this pass (all in files already owned by ADR-004's fix):

- **`_mergeExistingServicePeriod` (`veteranProfile.js`)** now has a second, narrower bypass alongside the existing `authoritativeDates` one: when the incoming record is from the **same source document** (`sameSource`, already computed for conflict detection) and explicitly reports `serviceStartDateDerived: false`, the merge treats it as that document's own correction of its own earlier guess and updates `serviceStartDate`/`serviceStartDateDerived` together. This is safe against a later, _uncorrected_ re-import regressing an already-fixed period: `serviceStartDateDerived: false` only ever comes from a printed extraction or from `DocumentIntelligenceBriefing.jsx`'s `_clearServiceStartDateDerivedIfEdited` forcing it false when the veteran's edited value differs from the raw re-extraction — never from an unedited re-scan, which reports whatever its own OCR/calculation produced (see `serviceEntryDate.integration.test.js`'s "does not let a later, uncorrected re-import regress…" case).
- **`pickServiceEntry` (`serviceEntryDate.js`)** now prefers any non-calculated (proven) period over a calculated one, regardless of date, falling back to the chronologically earliest only among periods with the same proven-ness. This is a **two-tier** split (proven vs. calculated), not the full veteran/printed/code_sheet ranking described in ADR-004 — see Open Issues below.
- **`getServiceEntry` (`veteranProfile.js`)** now treats a non-derived `profile.serviceStartDate` as an override when the periods-based answer is missing or still derived (never over an already-proven period). This is how FormsHelper's correction reaches `aiSystemPrompts.js`/`dossierExport.js`/the Service span without `FormsHelper.jsx` itself needing to change — the profile field FormsHelper already writes correctly is simply read with the right precedence.
- **`_syncFlatServiceStartDateMirror` (`veteranProfile.js`)** now refuses to replace an already-real (`serviceStartDateDerived: false`) profile date with a calculated one.
- **A versioned migration** (`SERVICE_HISTORY_SCHEMA_VERSION` bumped 1 → 2, `_repairStaleCodeSheetDerivedFlag`) clears `serviceStartDateDerived` on any period a Code Sheet has contributed to, for data saved before the `authoritativeDates` bypass existed.
- **`dossierExport.js`**'s Service Dates line now takes the end date from the SAME period `getServiceEntry()` resolved to (via `periodId`), not `profile.serviceEndDate` unconditionally, so a multi-document veteran no longer sees a hybrid range no single source states.
- **`DocumentIntelligenceBriefing.jsx`**'s live "(calculated from net service)" marker now clears the moment the displayed value differs from the untouched extraction, not only after Save.
- **`VKBViewer.jsx`**'s Entry Date edit now matches the corresponding `servicePeriods[]` entry within `dateUtils.isSameDate`'s existing 7-day tolerance (the same tolerance `isSameServicePeriod` already uses elsewhere), not exact string equality — `mergeDD214ServiceDates` (top-level) and the `servicePeriods[]` merge are independent code paths that can already disagree by a few days before a viewer edit ever happens.
- **`veteranKnowledgeBase.js`**'s `mergeDD214EvidenceTimeline` now upserts (replaces in place) the single service-entry timeline event per source document instead of appending a second one when a correction changes its date.

## Open issues (not fixed in this pass — outside file ownership or a product decision)

- **Code sheets don't reach `profile.serviceStartDate`/`dd214Data.entryDate`/the evidence timeline.** `autoPopulateProfile`'s document-type switch (`musterCallProcessor.js`) has no `case` for a code sheet's type (`c_file`) that updates service dates — only `service_record` does. `servicePeriods[]` and every consumer of `getServiceEntry()` are already correct after a code sheet import; the flat mirrors and timeline are not. Fixing this touches `musterCallProcessor.js`'s document-type integration, outside this fix's file ownership.
- **A My Packet "Save Profile" click can write a stale flat mirror back**, tracked to a React-state lifecycle issue in `MyPacket.jsx` (reads component state captured before a period edit's mirror sync ran). `MyPacket.jsx` is owned by another engineer beyond the Service span summary line.
- **`ProfileImportConfirmModal.jsx`** drops an explicit `serviceStartDateDerived: false` because its confirm handler only forwards fields that are both selected AND truthy. Not in this fix's owned-file list; flagged for whoever owns that modal.
- **Shape 1 (profile) and shape 2 (VKB) can still disagree after a single edit**, and import order can change the result (`pickServiceEntry`'s "earliest wins" vs. `mergeDD214ServiceDates`'s "a calculated date never displaces an already-authoritative one"). ADR-002 deliberately keeps these stores independent; unifying them is a product decision, not a bug fix — **flagged for Wren**: does a calculated period count as "proven" in "earliest proven period start" the same way in both shapes?
- **The full veteran > printed > calculated precedence ADR-004 described is not implemented** — `pickServiceEntry` only implements proven-vs-calculated as a tie-break, not a three-tier ranking, because there is no reliable signal in a period's own fields to distinguish "printed" from "veteran-supplied" once `userEdited` is set by _any_ field edit (see next point). **Flagged for Wren** if a stronger ranking is required (e.g. a real veteran DD214 for a later period should not be able to out-rank a veteran's own corrected earlier enlistment, which the current tie-break already gets right, but two non-derived periods from different sources with no chronological relationship would need an explicit tier to resolve correctly).
- **`_sourceForPeriod`'s `source` field is unreliable**: editing any single field on a period (e.g. MOS) sets `userEdited`, which is then read as `source: 'veteran'` for the date too, even if the date itself was never touched; conversely, a Muster Call correction doesn't set `userEdited` at all, so it reports `source: 'printed'`. No production consumer reads `source` yet (confirmed by grep); fixing this properly needs a per-field edit marker rather than one whole-period `userEdited` flag, which is a larger data-model change than this pass's scope.
- **ADR numbering collision**: this branch's ADR-004 and `fix/boot-kill-switch`'s `ADR-004-boot-migration-kill-switch-and-fail-open.md` are unrelated documents sharing a number. This ADR is filed as ADR-005 to avoid colliding with either on this branch, but one of the two ADR-004s will still need renumbering when both branches integrate into `main`.

## Consequences

- `_mergeExistingServicePeriod` now has two escape hatches from the "identity fields never merge" rule (`authoritativeDates` for a different, more-authoritative source; the new same-source bypass for that same document correcting itself) — any future change to this function must keep both, and keep them mutually exclusive in intent (authoritative-source correction vs. same-source self-correction).
- `pickServiceEntry`'s proven-vs-calculated tie-break is now load-bearing for every shape-1 consumer; a future caller must not reintroduce a raw "earliest by date" sort over periods that mix derived and non-derived rows.
- The schema migration establishes the pattern for any future stale-flag repair: version-gate it, make the repair function itself idempotent (check the specific stale signature, not "run once and trust it"), and run it inside `getServiceHistory`'s existing migration block.

## Amendment (ADR-007, 2026-09-27)

Each Open Issue above is now closed:

- **Code sheets not reaching `profile.serviceStartDate`/`dd214Data.entryDate`/the evidence timeline** — closed by the projection (`saveServiceHistory`'s flat-mirror/`dd214Data` projection; `projectServiceEntryIntoVkb`'s timeline projection). A code-sheet-sourced period now reaches every consumer the same way a printed or veteran-entered one does.
- **A My Packet "Save Profile" click writing a stale flat mirror back** — closed by the `saveVeteranProfile` chokepoint, which overwrites the payload's start-date fields with the current projection regardless of what stale component state supplied (see `MyPacket.jsx`'s `_saveProfileTab` and its `EXCLUDED_FROM_SOURCE_TRACKING` set).
- **`ProfileImportConfirmModal.jsx` dropping an explicit `serviceStartDateDerived: false`** — closed structurally: DD214Analyzer no longer sends `serviceStartDateDerived` through the import payload at all (see ADR-004's amendment); the modal instead reports `{serviceStartDateEdited}` metadata, and `_saveDd214ToProfile` creates a canonical period with correct provenance regardless of what the modal forwards.
- **Shape 1/shape 2 disagreement and import-order sensitivity** — closed by making shape 2's service-entry subset a projection of shape 1 (ADR-007 §2.5); there is no second independent resolver left to disagree with the first. Wren's flagged question ("does a calculated period count as proven the same way in both shapes") is resolved by construction — there is only one resolver now.
- **The full veteran > printed > calculated precedence not implemented** — closed by `serviceStartDateSource` (§2.2 of ADR-007), a real per-period provenance field distinct from the whole-period `userEdited` lock this ADR's tie-break was limited to.
- **`_sourceForPeriod`'s `source` field being unreliable** — closed by the same fix: `serviceStartDateSource` is written by the one function that changes a start date (`_setPeriodStart`) and is never inferred from an unrelated field's `userEdited` flag.
- **ADR numbering collision** — already resolved in commit `89bbccb7` prior to this ADR.

The cross-enlistment tie-break itself (§2.2/DR-1 of ADR-007) intentionally changes from this ADR's "proven beats calculated" two-tier rule to a chronological rule with a calculated-runs-late invariant. Owner decision recorded 2026-09-28 (ADR-007 §3): chronological is final — this ADR's own two-tier tie-break description for that one comparator is superseded, not merely pending; everything else in this amendment stands regardless.
