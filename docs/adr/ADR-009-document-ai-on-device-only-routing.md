# ADR-009: raw documents stay on the device - a fail-closed provider-routing boundary

**Status:** Accepted.
**Date:** 2026-09-29/30.
**Decided under:** owner decision E, 2026-09-29 ("RAW DOCUMENTS STAY ON THE DEVICE").
**Amended by:** decision F, 2026-10-01 (§3) - the AI is never the source of a DD-214 identifier field.
**Amends:** ADR-008 §4's first open issue (BlueButtonXRay/cfileAnalyzer/MyPacket's pasted-DD214 first-mention identifier gap) - see §5 below. Does not change ADR-008's own redaction mechanism (`_redactPiecesForSend`/`redactKnownValues`), which still runs on every `"context"`-classed call, on every backend.

## 1. Context

ADR-008 closed the identifier-leak gap for veteran data the app already knows (§2.4.1's provider boundary, `_redactPiecesForSend`). Its own §4 flagged what known-value redaction structurally cannot do: protect an identifier a document mentions for the _first time_ - before the app has ever seen it, and therefore has nothing to compare it against. `BlueButtonXRay.jsx`'s health-record chunking, `cfileAnalyzer.js`'s C-File OCR/page analysis, and `MyPacket.jsx`'s pasted-DD-214 extraction all sent a just-uploaded document's own raw text to `generateAI` for content analysis, on whichever backend (cloud or on-device) the veteran had configured. A veteran using only Cloud AI had every uploaded document - DD-214, C-File, Blue Button export, VA decision letter - sent off-device on first mention, identifiers included, with no redaction possible.

Decision E closes this a different way than more redaction: instead of trying to detect and strip an unknown identifier from free-form document text (unbounded, layout-dependent, never fully solvable - ADR-008 §4's own conclusion), raw document text is now categorically barred from ever reaching an off-device provider at all. The provider boundary in `unifiedAIService.js` enforces this for every backend, not per-tool discipline.

## 2. Decision

Every call into the provider boundary (`generateAI`/`generateAIWithImage` in `src/utils/unifiedAIService.js`) declares a **data class**:

- **`"document"`** - text derived from a document: an uploaded/dropped file, OCR output, a C-File page/segment, a DD-214/NGB-22, a VA decision letter, a Blue Button export, or letter/decision text the veteran pastes in. May reach an on-device engine only.
- **`"context"`** - the ADR-008 allow-listed structured veteran context (already identifier-redacted) plus the veteran's own typed question/statement. May reach any configured backend, on-device or off-device.

A call that omits `dataClass`, or supplies anything other than the exact string literal `"context"`, is treated as `"document"` - **fail closed, not fail open**. This is enforced in `src/utils/aiDataClassPolicy.js`'s `resolveDataClass`.

### 2.1 On-device definition

"On-device" means:

- The two in-browser engines - Warrant Council/WebLLM (`AI_MODES.SWARM`) and Wllama/WASM (`AI_MODES.WLLAMA`) - unconditionally (nothing they run ever leaves the process).
- Legacy local (`AI_MODES.LOCAL`) - unconditionally, same reasoning.
- A local llama.cpp server (`AI_MODES.LOCAL_SERVER`) - **only** when its _currently configured_ host resolves to loopback: `localhost`, the `127.0.0.0/8` IPv4 range, or `::1` (bracketed or bare). Everything else - `AI_MODES.CLOUD` (Gemini), and a `LOCAL_SERVER` pointed at any non-loopback host - is off-device.

`aiDataClassPolicy.js`'s `isLoopbackHost(hostOrUrl)` implements this by parsing the value as a real URL/hostname (`new URL(...)`), never by substring/prefix/suffix matching. This specifically rejects the lookalikes a naive check would accept:

- `localhost.evil.com` (a subdomain of an attacker's own domain, not `localhost` itself)
- `127.0.0.1.nip.io` (a wildcard-DNS service that resolves to `127.0.0.1` but is a five-label hostname, not a loopback address)
- `evil-localhost` / `notlocalhost` (substring hits with no host-boundary)
- Non-loopback private ranges (`192.168.x.x`, `10.x.x.x`) and non-loopback IPv6 (`fe80::1`)

The local-server check re-reads `localServerClient.getServerConfig().host` **live, on every call** - never a cached flag - since the veteran can repoint it to a different host at any time.

### 2.2 The fail-closed enforcement points

1. **Primary gate** (`generateAIInternal`, before any prompt assembly, DKB lookup, or ADR-008 redaction work runs): a `"document"`-classed call is refused immediately if no on-device engine is currently ready, via a typed `DocumentOffDeviceBlockedError` (`aiDataClassPolicy.js`). This is the fast, no-network path most callers hit.
2. **Per-backend defense in depth**: `generateWithCloudAI` and `generateWithLocalServer` each independently call `assertDocumentCallAllowed` before doing anything else (before scrubbing, serializing, or sending). This is the actual choke point every dispatch path - the primary attempt, the context-overflow fallback, and the general (mode-failed) fallback - converges on for these two backends, so none of them can reach an off-device transport by a different route. `generateWithWarrantCouncil`/`generateWithWllama`/`generateWithLocalAI` need no such check: they are unconditionally on-device.
3. **Fallback-chain gating**: `_handleContextOverflowFallback` never auto-escalates a `"document"` call to Cloud on a context-window overflow (previously the large-document behavior for every class). `_handleGeneralFallback` never retries a `"document"` call against an off-device fallback mode either - both return/rethrow the original error (already the typed `DocumentOffDeviceBlockedError` when that's what actually happened) rather than attempting an off-device backend and wrapping its own refusal into an opaque `"All AI modes failed"` message that would defeat the caller's `instanceof` check.

A `"context"`-classed call is never blocked by any of the above; it reaches whatever backend the veteran has configured, exactly as before this ADR, with ADR-008's redaction still applied.

### 2.3 The `onDevice` response contract

Every `generateAI` response - success, validation-failed, or a fallback result - carries `onDevice: true | false`, computed from the engine/host that actually generated the response (`_isModeOnDevice(usedMode)`; for `LOCAL_SERVER` this re-checks the live host, same as §2.1). Consumers must treat anything other than a strict `true` as off-device (fail closed) - this flag no longer decides anything about identifier fields (decision F, §3: the model is never their source), but stays the contract for any consumer that needs to know where a response was generated.

### 2.4 UX: the fallback a document feature shows

`getDocumentAIRouting()` lets a document-classed feature check, before calling `generateAI`, whether an on-device engine is ready and what off-device provider would otherwise have been used (for the notice below). This is an optimization over catching the typed error (skips a doomed attempt's setup work); the typed error thrown inside `generateAI` itself remains the authoritative enforcement point - both read the same live state.

When no on-device engine is available, a document feature:

1. Runs its existing local parser/pattern-matcher (the same one already used when no AI at all is configured) and shows whatever it finds.
2. Shows a short, plain-language notice (`aiDataClassPolicy.buildDocumentOffDeviceNotice`): _"Your documents are only read by the on-device AI, so this file was not sent to \<provider\>. Showing what the app's built-in reader found."_
3. Never shows a dead end or a silent failure - the veteran always gets a result (even if the local parser finds nothing) and an accurate explanation.

When an on-device engine **is** available, the feature works exactly as before - the document is sent to the on-device engine and the AI-derived result is shown.

## 3. Identifier fields inside a document call - decision F: the AI is never the source

**Decision F (owner, 2026-10-01) supersedes the earlier text of this section**, which let an on-device `"document"` call request identifier fields (name, DOB, SSN last 4, home of record, mailing address) on the reasoning that nothing leaves the device. That reasoning was about privacy; the measured problem is correctness.

**Why (measured wrong-value rate).** Three evaluation rounds on the owner's own scans showed the on-device model invents identifier values. On the final run of 5 scans the DD-214 Analyzer filled 14 of 25 identifier fields and **10 of those 14 were wrong**, some with values that appear nowhere in the document, and every one was pre-selected for profile import. A wrong identifier written to a veteran's profile is worse than a blank one, so no amount of "trusted device" framing justifies it.

**Rule.** The AI is never the source of an identifier field. Name (and its parts), date of birth, SSN (any part), service number, home of record and mailing address, shown or saved by the DD-214 Analyzer, come only from `dd214FieldExtractor.js` when its parser is confident. Otherwise the field is empty and the veteran types it in. Specifically:

- Neither DD-214 AI prompt (on-device or the cloud-sized one) asks for any identifier field, and the on-device prompt tells the model to omit them.
- A model that returns one anyway has it dropped when the response is parsed (`_parseDd214Json`): that step is an allowlist, so only the keys the two prompts request survive and an identifier filed under any other key or nested object ("SSN", "veteranName", "personal": {...}) never reaches the result or My Packet. `_applyRegexSafetyNet` then `_applyRegexSafetyNet` rebuilds every identifier field from the local parser alone. The `onDevice` response flag no longer changes this - an on-device model's value is not kept either.
- The extractor is confident-or-empty for every identifier field: a value made only of the form's own printed label or instruction wording (CITY, STATE, COMPLETE, ADDRESS, IF KNOWN, ZIP CODE, HOME OF RECORD...) is rejected, text that is another box's caption (STATION WHERE SEPARATED, ENTRY INTO ACTIVE DUTY, PAY GRADE, MEMBER REQUESTS...) is rejected too, a home of record must end in a real state (name, USPS code or older abbreviation such as CALIF or N.Y.), and a mailing address must start a street line, be a PO box, end in a ZIP code or have a city/state shape. This is a heuristic over noisy scans, not a proof: a caption outside these lists can still be captured, which is why every identifier box is editable and nothing is pre-selected.
- An empty identifier is a text box in the results panel. What the veteran types is stored on the result and always wins; it is offered to the profile import but never pre-selected.
- Nothing identifier-related is pre-selected in the profile import dialog, whatever its source, and the Knowledge Base and the structured copy filed in My Packet receive name, SSN last 4, date of birth or address only when the veteran ticked that box. Model responses, OCR text and extracted identifiers are not written to the browser console by `DD214Analyzer.jsx` or by the legacy on-device paths in `unifiedAIService.js` (generation config, raw response, vision response), so they cannot land in a captured bug report. Other console output elsewhere in the app is outside this ADR.
- **Place of birth (D21-3).** Place of birth is identifier-bearing under decision F. It is in neither prompt, it is not in the `_parseDd214Json` allowlist (a model that returns one has it ignored), the local parser has no such field (so it is simply empty), and the import dialog never pre-selects it. On 4 of the owner's 5 real scans the model returned the prompt's own placeholder text for it, and none of the forms has that box. The same holds for every other key in this class: next of kin, nearest relative (name or address), phone, email, service number and signatures are not model-schema keys and are never pre-selected (`NEVER_PRESELECTED_FIELDS`). `MODEL_SCHEMA_KEYS` was audited against this list.
- **Placeholder echoes (D21-3).** A model that returns the prompt's own template text for any field has not read the document. `buildPlaceholderDetector` (`dd214ModelOutputGuards.js`) derives the template strings from the two prompts' own schema literals, so the list cannot drift from the prompts, and `_parseDd214Json` drops any value (in any field, including inside lists and award objects) that matches one, plus bare type words ("number", "string"), date templates and 3+ way "A|B|C" alternatives. The comparison ignores case, spacing, punctuation and a trailing "(Block 8)", so "Unit and major command." is the template too, and a longer answer that contains a template of 10 or more characters ("Block 8: Unit and major command") is rejected. A "|" alternative is rejected when its parts are two or more of one prompt template's own alternatives ("RE-1|RE-2", "Honorable|General"); a value that merely contains a pipe ("HHC | 3-7 INF") is not. "true/false" is a bare type word. A **whole list** copied from a prompt (the prompt's complete example list for `documentTypes`, `specialQualifications`, an award's `devices`, `combatService.indicators` or `.deployments`, with the "etc" filler ignored) is dropped as one echo, while a genuine shorter list that resembles the examples (`["Airborne", "Ranger"]`) is kept; the one accepted cost is that a veteran whose real list is exactly the example list loses it. A single-word value is never treated as a template, because "DD214" or "Army" is a genuine answer.
- **Every model-written value (D21-7, identifier lens).** A model can file a name, an SSN-shaped string or an address under any key, not only the free-text ones, and in any shape (string, list, object, list of objects). `sanitizeModelOutput` (`dd214ModelOutputGuards.js`) checks each allowed key against the type it permits and scrubs every string in it. Dates must be date-shaped (ISO, `YYYYMMDD` or `MM/DD/YYYY`) and are dropped if they equal a known identifier; counts must be non-negative numbers up to 99,999 (a fractional length of service is fine); `foreignService`, `reenlisted`, `isCombat` and `hasVerifiedCombat` must be booleans (a `"true"`/`"false"` string is converted, anything else is dropped); service time must be `{years, months, days}` of counts; an award keeps only `name`, `abbreviation`, `sourceDocument`, `devices`, `deviceCount` and `isCombat`; `combatService` keeps only `hasVerifiedCombat`, `indicators` and `deployments`; every other key is text, limited to 80 characters for a code or name key (branch, rank, pay grade, MOS, character of service, separation type and code, and similar) and 300 for any other, so a sentence a model wrote into the wrong field is dropped (the four free-text fields are not limited). A value of the wrong type is dropped, never coerced into text. All strings go through `scrubText` plus known-value redaction (the saved profile and the identifiers the local parser read from this document). This runs at parse time, and again in `_applyRegexSafetyNet` **before** the merge with the local parser, so the name the parser read is available as a known value while the parser's own values are left untouched. The four free-text fields are scrubbed once more after the merge. This is bounded by what the app knows: a name the app has never seen (no saved profile, none read locally) has no shape and is not caught, whichever key it sits in; see ADR-008 section 2.9. Because of that limit, model-written text is treated as identifier-bearing: `extractionNotes`, `narrativeReason`, `memberRequests`, `foreignServiceDetails`, `lastDutyAssignment` and `commandTransferredTo` are never pre-selected in the import dialog (`MODEL_TEXT_FIELDS`), the narrative reason reaches the Knowledge Base only when ticked, and none of them (nor an unticked identifier) is in the structured copy filed in My Packet.
- **Enumerated fields and the known-identifier set (D22-3; supersedes the 80-character code-field limit and the "a name the app has never seen is not caught" limit in the bullet above).** A short code field is not allowed to hold text at all. A value that passes its list or shape is then checked a second time against known values, known birth dates, `scrubText` (SSN, address, phone shapes) and the person and place shapes, and is dropped if any of them would change it; the shape check narrows what the field may hold, the second check is the lock. A bare run of eight or more digits is never a `sglCoverage` amount.
  - _Fixed list or strict pattern, else dropped_ (`dd214EnumeratedFields.js`): `branch` (the known branches and guard/reserve forms), `component` (RA, ARNG, USAR, USN, USAF, USMC, USCG and similar), `componentFull` and `rank` (words from a rank/component vocabulary plus `E5`/`PO2`/`1st`-style tokens), `payGrade` (`^[EOW]-?\d{1,2}$`, E 1-9, W 1-5, O 1-10), `mos` (2-6 letters and digits with at least one digit, optionally followed by up to two `-` or `/` groups, never an SSN shape, or a Navy/Coast Guard rating), `reentryCode` (`RE-1A`, `1J`), `separationCode` and `separationProgramDesignator` (three characters), `separationAuthority` (a regulation reference: it must contain a digit and every word beside the numbers must be a regulation acronym or word such as AR, AFI, MILPERSMAN, paragraph, so a name or an address fails), `separationType`, `characterOfService`, `giBlStatus`, `securityClearance` and `sglCoverage` (vocabulary or amount), `masterRecordType` and every `documentTypes` entry (`DD`/`NGB` form numbers). A value that fails is dropped and never shown; it is not truncated, coerced or "cleaned". A value that also equals a known name token is dropped even if it fits the pattern (a three-letter surname in a code field). The shapes are heuristics, not proofs: a three-character surname that is not known to the app still fits the code pattern.
  - _Dates_ must be real calendar dates (`1984-02-30` is dropped) between 1930 and 15 years ahead. A date is also dropped when it equals a known birth date **in any of the readings and formats** the app or a document uses (ISO, `YYYYMMDD`, `MM/DD/YYYY` and `DD/MM/YYYY` both ways, two-digit years in both centuries, `15 Mar 1984`, `15MAR84`, `March 15, 1984`), in every date key (`masterRecordDate`, `dateOfRank`, `entryDate`, `separationDate`, `reserveObligationDate`).
  - _Known-identifier set._ Before each analysis, `loadKnownIdentifierSources` (`dd214KnownIdentifierSources.js`) gathers every store that can hold identifiers: the saved profile, the service history, the Knowledge Base `personal` and `serviceHistory` blocks, and the `extractedData`/`aiAnalysis` of every My Packet document; the local parser's own fields for this scan are added in `_applyRegexSafetyNet`. Names, address parts, numbers and birth dates from all of them redact model text by value and feed the date check. Each store is read with a 4-second limit. **A read that fails or times out fails closed (D22-3 remainder):** the set is then incomplete, so for that reading every model-written date and all model free text are dropped and the veteran is told plainly that only the values the app read itself are shown; the analysis still completes. A birth date read by the local parser from this scan's birth-date box joins the known set. A birth date is looked for under `dateOfBirth`, `dob` or `birthDate` (any case, with or without underscores) at any nesting up to four levels (a bounded search), and ISO timestamps and `15-Mar-1984` or `1984 03 15` forms are read; a store that holds it under a different key name is not seen.
  - _Genuinely free text_ (`lastDutyAssignment`, `commandTransferredTo`, `narrativeReason`, `memberRequests`, `foreignServiceDetails`, `extractionNotes`, `mosTitle`, `militaryEducation`, `specialQualifications`, award, deployment and combat-indicator text) is model text under decision F: scrubbed, known-value redacted, and stripped of person-, city- and ZIP-shaped text (`dd214ModelTextScrub.js`: titled names, `Last, First`, `First M. Last`, city with a state code or name, five-digit and ZIP+4 numbers). In sentences and unit lines (`prose`), and in 2-3 word award, school and deployment items (`short`), a stretch of two or more adjacent capitalized words that are not military, award, school or place vocabulary is removed as a probable name. Award, school and deployment items of more than five consecutive unknown capitalized words, a single unknown capitalized word (a lone surname the app has never seen), a name written in lowercase, and a spelled-out rank that is followed by an ordinary word are not caught; this is a limit of a vocabulary-based check, which is why none of this text is pre-ticked. The words after a ship prefix (`USS`, `USNS`, `USCGC`, `HMS`) are kept, because a ship name such as `USS Abraham Lincoln` has the shape of a person's name and is a duty station; a name placed after such a prefix is therefore not caught. `mosTitle`, `militaryEducation`, `specialQualifications`, `awards` and `combatService` are never pre-ticked and reach the profile, service history, the Knowledge Base and My Packet only when ticked. The dialog shows each list or object as one text row (`militaryEducation`, `specialQualifications`, `awards` as award names, `combatService` as its deployments and indicators); ticking the row files the analysis value, not the edited text, and an unticked row files nothing, including no award, deployment or `mosTitle` in the service history. An award `sourceDocument` (a file name) goes through `redactFileNames`. Where the local parser read the same free-text field from the document, its value replaces the model's.
- **Decision G: nothing the model read is pre-ticked (owner, 2026-10-03).** Measured on 34 real readings of 9 DD-214 service fields, the on-device model gave 65 correct, 124 empty and 117 wrong values (pay grade wrong 31 of 34, entry date never right), and 107 of 153 pre-ticked service rows were wrong. A row in the import dialog is therefore pre-ticked only when its value came from the local parser (`dd214FieldExtractor.js`) with confidence, in every field. The parser value is shown first. A model value appears only where the parser has none, unticked, labelled "Read by the AI" with a short instruction to check it against the document. Where the two disagree the parser value is shown and the model's is not offered (`dd214ValueSources.js`). The result card and the import dialog state how many values came from each source, and Import with no row ticked saves nothing. Rows are proved in component tests and in `tests/e2e/dd214-parser-first.spec.ts` (a reply filling every field plus a parser reading three pre-ticks exactly those three, and Import untouched saves exactly those three).
- **Parser text is scrubbed like model text (D23-1).** Parser-read free text and lists (military education, awards, special qualifications, remarks, unit and duty lines) go through `sanitizeParserFields` (`dd214ParserTextGuards.js`) before they are shown or saved: a length cap per item, `scrubText`, known-value redaction, person/place/ZIP shape removal and removal of date-of-birth and SSN shapes; an item that is mostly redaction marks, or longer than a real entry of its kind, is dropped. The cause of the page-run capture was a greedy block match with no end anchor in `dd214FieldExtractor.js`; block captures now end at the next printed box.
- **Rowless fields are never stored (D22-3 remainder).** A key with no visible row in the import dialog (`masterRecordDate`, `dd214Count`, the parser's remarks and station lines) is not written to the profile, Knowledge Base or My Packet: it gets a row or it is not stored. MOS, AFSC and rating codes need a strict per-branch shape that cannot match a date, an SSN fragment or a bare 4-8 digit number, and `dd214Count` accepts only a small plausible count.
- **Accepted residue in free-text rows (D22-3(d)).** One unknown uppercase word and a bare 4-digit number can survive in free-text rows. This is acceptable only because those rows are never pre-ticked and each is labelled and editable.
- **A model reply is parsed as JSON first (D22-5).** `_parseDd214Json` (via `dd214JsonReply.js`) tries `JSON.parse` on the reply after fence removal; only if that fails does it take the first balanced object and strip `//` and `/* */` comments and trailing commas with a string-aware scanner that never touches text inside quotes. The earlier regex removed the rest of the line inside a quoted value, so a unit or transfer line containing `//` failed to parse on 4 of 7 readings of one real scan. The parse error still never carries the reply.
- **Text normalising and what shape matching cannot see (D22 final).** Before any name or place shape is matched, model text is normalised: Unicode NFKC (full-width digits and letters become plain ones) and every Unicode space, no-break space and line break becomes one plain space, so a name split by a line break or joined by a no-break space, `City,<line break>ST` and a ZIP in full-width digits are caught like their plain forms. Letters are matched with Unicode classes, so accented names (`José Núñez`) count as names. A city with a state code but no comma (`Springfield IL`) is removed for state codes that are not also ordinary words. **Out of reach, by design:** a name written entirely in lowercase (`zorblax quindle`) has no shape to match - it is indistinguishable from ordinary words - and is not removed by the shape rules; only a name the app already knows is removed by value, and the text stays unticked and editable for exactly this reason. The same holds for a single unknown surname.
- **Reply wrapping (D22 final).** A reply that is valid JSON but not an object (an array wrapping the object, a bare string) is not a reading as it stands: the first object inside it is used, and a reply with none is a parse error, never an empty analysis.
- **Confirm before save (D21-4).** Nothing is written to the profile or the Knowledge Base from the DD-214 Analyzer until the veteran confirms the import dialog. Reading a dropped scan calls `processFormationDocument(..., { deferPersist: true })`, which skips every write; the result is kept in memory. Confirming the dialog stores the service data (periods, awards, deployments, the archived document) with `stripIdentifiersFromFormationResult` applied (name, date of birth, VA file number and claim number removed), so those reach the profile and Knowledge Base only through the boxes the veteran ticked. The flat profile fields (branch, dates, MOS, character of service) are written only from the boxes ticked, in the dialog's own values: confirming no longer re-runs the Muster parser's `autoPopulateProfile`, which had written them whatever was unticked, from a different parser than the one shown. **The archived document is a deliberate exception:** the document text (`dd214Data.extractedText` up to 10,000 characters, the Knowledge Base document text and the My Packet `rawText`) and the parser's `extractedData.raw` are the veteran's own document and still contain whatever is printed on it, including name, date of birth and SSN, whichever boxes were ticked. Only the structured fields are identifier-free after an unticked import. Closing the dialog without confirming leaves both unchanged, and the results card says so; after a confirmed import it says what was saved instead. **The rule, with no exception (D22-4):** every analyzer tool (DD-214 Analyzer, Blue Button X-Ray, Decision Decoder, C-File Analyzer) writes nothing to the profile, Knowledge Base, My Packet or timeline until the veteran confirms. The C-File Analyzer reads a dropped file with `deferPersist` and `omitIdentifiers` and shows what it found with a Save to my records button that lists what will be kept (conditions, timeline events, the document). Closing the screen without it leaves localStorage and IndexedDB unchanged. Saving files the document once under its real type (the same keyed write as the other tools, so saving again or analysing the same letter again adds nothing) and merges the conditions and timeline events; name, date of birth, VA file number and claim number are not saved as fields (a claim letter dropped into either analyzer carries the last two). The Blue Button X-Ray no longer files the record when AI Scan is clicked; only its explicit Save to My Packet button does. The Decision Decoder writes nothing to either store. Muster Call keeps its own review step and default behaviour.
- **No identifier in a bug report (D21).** A file name can carry the surname or the last four digits of an SSN. `redactFileNames` (`piiScrubber.js`) replaces anything shaped like a path or a name with a document, image, office, e-mail or media extension by `[file name]`, independent of any known value; a spaced name swallows up to eleven words before the extension (over-redacting the log line rather than leaking a surname), and code and data formats the app itself loads (`js`, `css`, `html`, `json`) are deliberately left alone. A name with no extension or an unlisted one has no shape, so every file the veteran drops or picks (a capture-phase `drop` and file-input `change` listener installed by `initializeErrorCapture`) is also remembered by full name for the session and redacted wherever it appears. The console interceptor applies both on capture and on read; `cleanReportData` applies them to every text field of a report, and `BugSquasher.jsx` runs the copy stored in My Tickets and every field posted to the off-device endpoint through it. Remembering is by full file name only: the bare name without its extension is not, and a file that reached the app without a drop or file-picker event (pasted, or created in code) is covered only by the shape rule.

Non-identifier AI extraction (service dates, character of service, MOS, awards, deployments and so on) is unchanged.

An off-device prompt for a document never exists at all under this ADR - there is no code path where a `"document"`-classed call's prompt reaches an off-device backend, so the question of what that prompt may ask for is moot. Decision F is why the on-device prompt no longer asks for them either. See [ADR-008](./ADR-008-ai-context-data-minimisation.md) for the matching rule on stored data.

## 5. ADR-008 §4 cross-reference: first-mention limitation resolved for off-device providers

ADR-008 §4's first open issue is now resolved **for off-device providers specifically**: `BlueButtonXRay.jsx`, `cfileAnalyzer.js`, and `MyPacket.jsx`'s pasted-DD214 path are all `"document"`-classed under this ADR, so none of them can reach Cloud AI (or a non-loopback local server) regardless of whether an identifier inside the document has ever been seen before. The underlying redaction problem ADR-008 §4 described - detecting an unknown identifier in free text - is not solved (there is still no such detector), but it no longer matters for the off-device leak it was flagging, because the text carrying it never leaves the device. A shared-device risk (multiple veterans using the same on-device install) is a different, out-of-scope threat model, unaffected by this ADR either way.

## 6. Consequences

Positive:

- A veteran with only Cloud AI configured can no longer have a document's content - or a first-mention identifier inside it - sent off-device, regardless of which of the ~15 document-analysis call sites they use.
- Every document feature degrades to its existing local parser plus a plain-language notice instead of silently failing or leaking, when only an off-device AI is configured.
- The fail-closed default (`resolveDataClass`) means a _new_ call site added later without a `dataClass` declaration is safe by default (treated as document) - and the source-scan test makes forgetting the declaration entirely a build-time-visible failure rather than a silent gap.

Costs / visible behavior changes:

- A large document that overflows a small on-device model's context window (e.g. legacy Local's 4096-token limit) no longer auto-falls-back to Cloud, even if Cloud is configured - `_handleContextOverflowFallback` now returns null for `"document"` calls before ever considering it. The veteran sees the original overflow error (truncation guidance) rather than a cloud-assisted result. This is a deliberate consequence of the new boundary, not a defect - the alternative is exactly the leak this ADR closes.
- Pathfinder's strategy analysis (`pathfinderEngine.js`) is fail-closed to `"document"` unconditionally, even for a veteran who only ever types free-text symptoms and never uploads anything - because the call site cannot distinguish the two cases with the `additionalContext` field as currently structured. A veteran with only Cloud AI configured and no on-device engine loaded will see Pathfinder's typed-error message instead of a result, even with no document involved. Flagged in openIssues.

## 7. Verification

`src/utils/aiDataClassPolicy.test.js` (loopback host parsing including both adversarial lookalikes named in the brief, the fail-closed data-class default, the typed error and its `.code`/`.providerLabel`, and the notice builder), `src/utils/unifiedAIService.documentRouting.test.js` (the real `generateAI` against every backend in turn: Cloud and a non-loopback Local Server both refuse a document call and make zero network/`chatCompletion` calls even with no `dataClass` declared at all; a genuinely loopback Local Server, Warrant Council, and legacy Local all accept one and mark the response `onDevice: true`; a context call still reaches Cloud with `onDevice: false`; a general-fallback scenario where an on-device backend fails for a reason unrelated to routing never crosses to an off-device fallback), `src/__tests__/aiCallSiteDataClass.sourceScan.test.js` (every `generateAI(` call site in `src/` declares a `dataClass`, including self-checks on the scanner's own regex/paren-balancing/comment-skipping logic), and `src/components/DD214Analyzer.visionResponseContent.test.js` (the unrelated pre-existing vision-path bug fixed alongside this work - see §8).

End-to-end (`tests/e2e/adr009-document-routing.spec.ts`, `vite --mode e2e`'s fake on-device engine plus a `page.route()`-stubbed cloud endpoint, never a real provider): DD-214 Analyzer, Blue Button X-Ray, C-File Analyzer, Decision Decoder, and Muster Call's import-time C-File analysis each prove, in a real browser, that a cloud-only configuration never sends a fixture document's unique marker to the stubbed cloud (zero matching requests) while the local parser's result and the plain-language notice both show, and that an on-device configuration's fake engine actually receives the document and the feature completes. ## 8. Open issues (not built in this pass, flagged for the owner)

- **RESOLVED by decision F (2026-10-01): DD214Analyzer's on-device prompt excludes identifier fields, permanently.** The earlier plan to request them again on an on-device call and trust the `onDevice` flag was dropped after the measured wrong-value rate in §3.
- **Pathfinder's fail-closed-to-document default blocks a text-only veteran.** See §6 - `pathfinderEngine.js` cannot currently distinguish "additionalContext is free-typed notes" from "additionalContext is OCR'd document text" at the call site. A real fix (e.g. a separate flag `Pathfinder.jsx` sets when `additionalContext` actually came from `analyzeDocument`) is a product/UX call, not made unilaterally here.
- **`dualLLM.js`'s document-by-default has exactly one live caller today** (`legalAnswerer.js`'s eCFR RAG path, via `AskTheRegs.jsx`'s override to `"context"`). Its conservative default is intentional (see its own header comment on future document-analysis use), but is untested against a _second_ real document-classed caller, since none exists yet.
- **The e2e suite's Muster Call coverage is boundary-level, not UI-level** (see §7) - a regression in `quickScanCFile`'s classification heuristic that stopped a genuine consolidated C-File from ever reaching `buildSegmentedCFileResult` in the first place would not be caught by this suite. That heuristic (and its 50-page/multi-type threshold) predates this ADR and is unrelated to data-class routing.
